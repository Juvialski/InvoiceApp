# Engoryx CRUD and RBAC Matrix

Status: Wave 4A current-state audit, updated 2026-08-30. This matrix covers shipped Engoryx workflows on the Wave 4A branch. It does not authorize roadmap expansion or tenant switching. Actions are grouped only when they share the same UI gate, server boundary, database authority, and history rule; the Action cell lists the exact operations covered.

The audit follows this chain for every row:

`visible UI affordance -> effective frontend permission -> server/RPC/service guard -> company-scoped RLS/database invariant -> audit/history behavior`

Static source, contract, and domain tests are evidence for the implementation. Authenticated Supabase/RLS replay, production provider delivery, and authenticated browser role smoke tests remain separate validation evidence; this local checkout has empty Supabase environment values and cannot claim those live checks.

## Permission and role notation

- `✓` means the seeded role contains every permission named in the row and the current UI exposes the supported action.
- `—` means the seeded role does not contain the complete permission bundle, or the row is not a supported action for that role.
- `GRANT*` means a custom member override can grant the action only when every named permission is effective and no explicit deny applies. It cannot cross the deployment-company boundary or grant a non-assignable permission.
- `DENY` means an explicit custom deny removes the permission from the effective set and the UI/backend must fail closed.
- `ROLE` means the permission is role-controlled/non-assignable for member overrides.
- `BLOCK` means a suspended or revoked membership has no effective company permission.

Seeded role bundles are taken from `company_role_permissions` and later domain migrations. Company Admin receives the catalog, Finance receives finance/invoice/project/cash and safe aggregate/report permissions, Payroll receives workforce/payroll permissions, and Viewer receives read-only project/invoice/expense/vendor/aggregate/report permissions. Role labels are display presets only; the runtime checks permission keys and active deployment-company membership.

## Audit conclusions and evidence boundary

- The shipped UI now uses effective permission keys for route visibility and action availability. Composite actions are all-of checks; a single related permission no longer advertises a cross-domain mutation that the server will reject later.
- The server/Assistant path is not the authority by itself. Supabase RPCs, RLS, company-bound foreign keys, active membership, lock/recheck logic, and audit/history triggers remain authoritative. `SECURITY DEFINER` hardening functions pin `search_path` where applicable.
- Archive is visibility/lifecycle organization. VOID or reverse removes active financial meaning while preserving history. Confirmed settlement and imported/provider evidence are not silently deleted or rewritten.
- `COMPLETE` describes the implemented contract and focused static/domain coverage. It does not imply that this local environment has authenticated Supabase, Storage/RLS, provider-email, or production-browser evidence. Those are called out separately in the Wave 4A goal-state checkpoint and final handoff.
